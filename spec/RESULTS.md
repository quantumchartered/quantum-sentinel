## Current code: BLOCKED / REJECTED always release the fence

FOUND BY TLC, NOT YET FIXED IN CODE. Worker 1 claims the replacement and stalls past its lease. Worker 2 re-claims it (attempt 2), passes revalidation and sends. Worker 1 resumes, its revalidation is BLOCKED (for example a transient balance-read error) and it writes NOT_SENT. A transfer is now live with no fence, so a person can approve a second replacement, which is also sent. Planned fix in packages/db/src/execution.ts: release only when executions.attempts = 1; otherwise keep the payment UNCERTAIN and escalate.

## Skip revalidation before sending

Within this model the approval's own checks and the unique index already cover it: FAILED never becomes live again (assumption A1). Revalidation still matters for what the model leaves out (balance, beneficiary, approval expiry).

## Retry without looking the request_id up first

With a stable request_id the provider de-duplicates the retry (assumption A2). The lookup avoids relying on that alone.

## Let two workers hold the same execution at once

Both send the same request_id, which the provider de-duplicates, and the release rule counts attempts, not lease holders.
